# Monetization receipts (src/server/Monetization.luau)

- DataStore "PurchaseHistory", key `{PlayerId}_{PurchaseId}`. Values: `{status="pending", at}`, `{status="done", at}`, or legacy `true` (meaning done, from before sprint 4).
- Flow (sprint 4): UpdateAsync only reserves (writes pending). Then the grant runs outside UpdateAsync (handlers may yield). Then a second UpdateAsync marks it done. If the grant fails or returns false, RemoveAsync drops the marker and the decision is NotProcessedYet. If marking done fails, it still returns PurchaseGranted.
- Why: a grant inside the UpdateAsync callback could run twice when the callback is re-run.
- Sprint 5: every attempt writes its pending marker with its own `token` (a GUID). It grants only if the value UpdateAsync returned has that token. Mark-done writes only over our own token; if another attempt took the receipt over, it leaves that marker and returns NotProcessedYet. Known limit: if a handler yields past 120 s and another server takes over meanwhile, both still grant. Tokens can't stop that, because the grant and the done-write can't be made atomic.
- Sprint 6: product handlers must not yield. The grant runs right after the reserve's token check, through `grantWithoutYield` (coroutine.resume). If it yields, it's closed and counts as a failed grant (the marker is removed, NotProcessedYet). PENDING_TIMEOUT is now 600 s, exposed as `Monetization._PENDING_TIMEOUT`. This closes the sprint-5 "known limit" in practice: a stale takeover would now need a DataStore call to stall for 600 s.
- A pending marker younger than PENDING_TIMEOUT (600 s since sprint 6) means busy → NotProcessedYet. An older one is taken over. That's safe only because Coins aren't persisted: a crashed server loses its grant along with it. Revisit this if purchases ever save to a DataStore.
- `Monetization._processReceipt(receipt, store, grant, buyer)` is a test hook; `Monetization.cloud.spec.luau` uses a fake store.
