# Monetization receipts (src/server/Monetization.luau)

- DataStore "PurchaseHistory", key `{PlayerId}_{PurchaseId}`. Values: `{status="pending", at}`, `{status="done", at}`, or legacy `true` (meaning done, from before sprint 4).
- Flow (sprint 4): UpdateAsync only reserves (writes pending). Then the grant runs outside UpdateAsync (handlers may yield). Then a second UpdateAsync marks it done. If the grant fails or returns false, RemoveAsync drops the marker and the decision is NotProcessedYet. If marking done fails, it still returns PurchaseGranted.
- Why: a grant inside the UpdateAsync callback could run twice when the callback is re-run.
- Sprint 5: every attempt writes its pending marker with its own `token` (a GUID). It grants only if the value UpdateAsync returned has that token. Mark-done writes only over our own token; if another attempt took the receipt over, it leaves that marker and returns NotProcessedYet. Known limit: if a handler yields past 120 s and another server takes over meanwhile, both still grant. Tokens can't stop that, because the grant and the done-write can't be made atomic.
- Sprint 6: product handlers must not yield. The grant runs right after the reserve's token check, through `grantWithoutYield` (coroutine.resume). If it yields, it's closed and counts as a failed grant (the marker is removed, NotProcessedYet). PENDING_TIMEOUT is now 600 s, exposed as `Monetization._PENDING_TIMEOUT`. This closes the sprint-5 "known limit" in practice: a stale takeover would now need a DataStore call to stall for 600 s.
- Sprint 7 (replaces the sprint-6 cancel): `runGrant` runs the handler in a coroutine and checks coroutine.status. If it yielded, it is NOT closed (cancelling could double-grant or leave half-done effects). processReceipt warns, returns NotProcessedYet and keeps the pending marker (no RemoveAsync). When the handler finishes later and returned true, `markDone` records done (own token only). If it fails late, the marker is left to go stale. PENDING_TIMEOUT is now 180 s. Handlers still must not yield; this is only a safety net.
- Sprint 8 (replaces the takeover): PENDING_TIMEOUT is gone. ANY pending marker = busy, forever; only the attempt that owns its token replaces it. Values now also include `{status="released", at, token}` (refused or failed grant), which can be reserved again. RemoveAsync is no longer used. The handler runs via task.spawn (`runGrant`); still running → NotProcessedYet. Late results are written by `keepWriting` (UpdateAsync over own token, task.wait backoff 0.5 s doubling to 30 s, until the call succeeds). A failed reserve also spawns a release, in case the write landed. A failed sync mark-done returns PurchaseGranted and retries in the background.
- Known cost of no takeover (sprint 8, eased in sprint 9 by the 24 h stale rule): a server that dies between reserve and the final write leaves the purchase stuck pending for a day.
- Sprint 9: a pending marker older than STALE_PENDING (24 h), or with no numeric `at`, counts as released (exactly 24 h old is still busy). `keepWriting` gives up after MAX_RETRIES = 10 attempts. A failed reserve no longer releases blindly: `releaseIfOurs` waits RETRY_FIRST, GetAsync, and releases only if our token is there (if GetAsync fails it releases anyway; the write is token-safe). `inFlight` counts keepWriting, releaseIfOurs and running grants; BindToClose `drain`s up to 25 s.
- Known cost of sprint 9 (accepted trade-off of stale + retry cap): if a YIELDING grant succeeds but its done write never lands (10 failures, or shutdown past 25 s), Roblox keeps retrying (it got NotProcessedYet) and a day later the stale takeover grants it again. Sync grants answer PurchaseGranted, so Roblox doesn't redeliver them.
- Sprint 10: `startHeartbeat` refreshes our pending marker's `at` every HEARTBEAT = 60 s (via `clock.delay`, writeOverOurs with `onlyPending` so it can't undo done/released). It runs while a yielding grant runs and inside keepWriting; it stops on finish/give-up. A pending marker with no numeric `at` is now busy, and the reserve restamps it (same token, `at = now`). SHUTDOWN_WAIT = 20. All warns go through `log.warn` (hook for specs). `_test` also exposes HEARTBEAT, log, passHandlers, productHandlers.
- Known cost of sprint 10: a handler that never returns heartbeats forever, so its receipt stays busy for good (it no longer goes stale). The sprint-9 cost (a given-up done write can be granted again after 24 h) still stands.
- Sprint 11: a heartbeat stops (one warn naming the key) once its next beat would be past MAX_HEARTBEAT_AGE = 1800 s from its start: last refresh at +1800, then stale STALE_PENDING later. This replaces the sprint-10 "busy forever" cost, but a handler yielding > 30 min + 24 h can be granted twice (its late write lands on nothing). The reserve restamps an `at`-less marker once (`restamped = true`); an `at`-less restamped one is busy and untouched. A give-up in keepWriting sets `gaveUp[key] = token`; processReceipt then answers NotProcessedYet before reserving, for that server's lifetime (both done and released give-ups).
- Sprint 11 hooks: `_processReceipt`, `_RETRY_FIRST`, `_test` exist only if `RunService:IsStudio()`. `_test` is frozen; use `setClock({now,wait,delay}|nil)`, `setWarn(fn|nil)`, `gaveUp(key)`, `clearGaveUp()`. Outside Studio the spec runs only a "hooks are absent" test, so a non-Studio cloud runner doesn't really test receipts. Spec `useTimedWait()` makes fake `wait` suspend until `fake.advance` reaches it.
- Sprint 12 (replaces the sprint-11 hooks line above): `Monetization._test` exists everywhere and is frozen; its functions error unless wired (IsStudio() at load, or `_test.enable()`, which the spec calls at load). `_processReceipt`/`_RETRY_FIRST` are gone: use `_test.processReceipt`, `_test.RETRY_FIRST`; `passHandlers()`/`productHandlers()` are now functions. `gaveUp(key)` returns a copy of `{status="done", token, at}`.
- Sprint 12 receipt logic: each try is an `Attempt` table (store, key, token, purchaseId, reservedAt, capped). The heartbeat window is reservedAt..reservedAt+1800, shared by the grant heartbeat and keepWriting's; the stop warn fires once per attempt (`capped`). Only "done" blocks: the cap during a running grant or a pending done write records gaveUp, and so does a done give-up. A released keepWriting clears that attempt's entry, and so does a write that lands over our own marker. Entries expire GAVE_UP_TTL = STALE_PENDING + 1800 after `at` (exactly TTL is still blocked). A done write that lands on someone else's marker keeps the block, on purpose.
- Spec runs on a fake clock (sprint 10: `fake.advance(s)` fires queued `clock.delay` timers; plain fake `wait` does not, so heartbeats don't shift UpdateAsync call counts in older tests; warns are recorded in `fake.warns`): `Monetization._test.clock.now/wait` are swapped per test (wait records + returns at once, so background retries finish synchronously). Yielding grants use coroutine.yield and are resumed with task.spawn(thread). The spec's DataStore fake needs GetAsync.
- Testing in Studio: the Studio place isn't Rojo-synced. To run the spec without editing the place, start a playtest and paste the module's receipt code and the spec into execute_luau (Server).
- `Monetization._processReceipt(receipt, store, grant, buyer)` and `_RETRY_FIRST` are test hooks; `Monetization.cloud.spec.luau` uses a fake store.
